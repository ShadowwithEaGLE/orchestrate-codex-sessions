# Codex 多 Session 混合编排

用最小充分的工作单元完成任务。核心判据是：工作完成后，完整执行轨迹能否安全丢弃，只保留压缩结果。能丢弃时使用会话内 subagent；需要持续身份、状态、交接或用户介入时使用侧边栏可见任务。不要把拆分本身当成质量。

**不可绕过的派发门：** 调用任何委派工具前，包括 `spawn_agent`、创建可见任务或 fork，必须先输出“派发前声明路由”表格。没有表格就不得委派；Level 1 内部代理也不例外。

## 服从顺序

1. 服从用户本轮目标、授权和禁止项。
2. 阅读并服从当前目录适用的 `AGENTS.md`；它与本 Skill 冲突时，以 `AGENTS.md` 为准。
3. 服从当前工具的能力、并发上限、审批和生命周期规则；不要假设某个 thread/subagent 工具一定存在。
4. 仅在前三层没有规定时使用本 Skill 的默认值。

若缺少创建可见任务、subagent、wait 或 worktree 能力，说明边界并执行仍可安全完成的最小部分；不要伪造委派或验收。

## 先选择工作单元

先回答：

1. 用户最终要看到什么，什么证据才算完成？
2. 完整执行轨迹能否在返回压缩结果后安全丢弃？
3. 哪些状态必须跨轮次保留，哪些只是一次性中间状态？
4. 谁拥有最终交付，用户是否需要直接进入该工作单元？
5. 是否需要独立 project、branch、worktree、正式交接或失败恢复？

| 级别 | 结构 | 本质 |
|---|---|---|
| Level 0 | 主任务直接完成 | 工作集中，委派收益低 |
| Level 1 | 主任务 + 会话内 subagent | 可丢弃的短期委派，主任务保持唯一最终所有权 |
| Level 2 | 可见主任务 + 可见交付任务 + 必要的 Level 1 subagent | 需要持久身份、状态、独立所有权或用户可寻址性的交付 |

只有以下条件全部成立时才使用 Level 1：

- 能在当前主任务结束前完成；
- 主任务保持唯一最终交付所有权并负责整合与验收；
- 用户无需直接进入、持续追问、纠偏或恢复该子任务；
- 完整轨迹可压缩为结论、补丁、`file:line` 或验证证据后安全丢弃；
- 失败后可安全重新派发，不会丢失关键业务状态；
- 不需要独立 project、branch、worktree、长期运行环境或正式上下游交接；
- 与其他执行单元没有重叠写入。

出现以下任一情况时选择 Level 2：

- 状态或执行历史必须跨轮次保留；
- 用户需要直接进入任务继续追问、纠偏或恢复；
- 工作单元承担独立交付所有权；
- 下游必须正式消费其接口、产物、manifest 或验收结果；
- 需要独立 project、branch、worktree 或长期环境；
- QA、Repair 或外部等待需要可恢复、可审计的过程；
- 完整历史无法安全压缩丢弃；
- 主任务结束后，该工作单元仍有独立存在价值。

复杂度、耗时、跨模块、修改文件、指定模型或推理强度都只是信号，不能单独决定级别。用户已明确选择工作结构时，用户选择优先于“从 Level 0 开始”的默认启发式。

## 明确授权边界

- 用户显式调用 `$orchestrate-codex-sessions` 并要求实施时，视为授权协调器在当前本地任务范围内按上述判据选择 Level 0、Level 1 或创建必要的 Level 2 可见任务；不需要逐个重复询问。
- 用户显式调用本 Skill 但只要求计划、比较、审查或建议时，保持只读，不创建任务或修改项目。
- Skill 被隐式触发本身不扩大授权：可直接使用 Level 0/1；若判断需要 Level 2，先列出拟创建的可见任务并取得一次确认。用户已明确要求多 Session、独立任务或侧边栏可见任务时，无需再次确认。
- 用户只要求计划、比较或建议时，停在只读分析和编排方案，不创建可见任务或修改项目。
- 用户已明确要求实施时，在既定本地范围内继续执行，不重复索要同一授权。
- 外部写入、发布、推送、权限变更、破坏性操作和明显扩展范围仍需单独授权。

## 派发前声明路由

在第一次委派前必须输出下表，每个工作单元一行；不得用自由叙述代替或省略列：

| 工作单元 | Level | 侧边栏可见 | 执行载体 | 所有权 | Depends on | 初始状态 | 选择理由 | 完成证据 |
|---|---|---|---|---|---|---|---|---|
| ... | 0 / 1 / 2 | 是 / 否 | 主任务 / `spawn_agent` / 可见任务 | 主任务 / 独立交付 | 无 / ... | ready / blocked / pending | ... | ... |

明确区分“内部临时 subagent”与“用户可见任务”，并区分“现在创建”与“依赖满足后才运行”。Level 1 不需要创建侧边栏任务；Level 2 未通过可见性验收前不得声称编排已建立。

## 执行工作流

### 1. 建立真实边界

- 确认真实项目根目录、当前 checkout/worktree、适用规则和已有改动。
- 亲自完整阅读奠基性文档，以及即将修改的准确代码。不要把这两类阅读委派给 subagent。
- 把最终可见结果、数据口径、隐私/联网/权限边界和完成证据写成 Acceptance。
- 发现重要歧义时列出解释和影响；能安全采用最小默认值时，标明假设后继续。

### 2. 画依赖与所有权图

- 按交付接口和风险边界拆分，不按文件数量机械拆分。
- 为每个可见任务写明 `Owns`、`Must not edit`、前置条件、交付物、验证命令和完成条件。
- 有接口依赖时串行，例如 Core → UI → Package/QA。
- 只读且互相独立的侦察可以并行。
- 可见任务不等于文件隔离。共享 checkout 中有重叠写入时必须串行；真正并行写入要求不重叠所有权或独立 worktree。

### 2.1 依赖与交接是硬门，不是提示

- 为每个任务声明 `Depends on`、`Produces`、`Consumes`、`Handoff gate` 和 `On success`。没有这些字段就不要并行派发有产物依赖的任务。
- 下游任务可以预先创建为可见会话，但在依赖满足前状态必须是 `blocked`：其任务书只能说明等待条件，不得开始实现、猜测接口或以简短回复结束。
- 上游完成后不得自行决定下游可启动。协调器必须先核验实际产物、测试结果和未验证项，再向下游发送结构化交接包并触发其下一轮。
- 交接包最小格式：

```yaml
status: ready_for_handoff
produced: [artifact paths]
manifest: path or null
verification: [actual commands and results]
failed_or_unverified: [items]
next_task: canonical task name
next_action: exact consumption step
```

- 下游收到交接包后先 ACK：确认所有消费文件存在、manifest 可读、接口/数据版本匹配；ACK 通过才转为 `running`。不通过则保持 `blocked`，由协调器创建最小 Repair。
- 对资产管线，manifest 必须提供 `source -> consumer` 映射和格式验证（例如 alpha、尺寸、许可证或校验和）；消费 UI 只能引用 manifest 目标，不能猜文件名或继续引用旧资产。
- 协调器监听的是“验收通过的交接包”，不是“任务文字说完成”。这条规则也适用于 UI → QA、Core → UI、生成资产 → 集成等所有链路。

### 3. 选择是否创建 `AGENTS.md`

- Level 0 或仅有一次性只读 subagent 时，不要为了形式新建 `AGENTS.md`。
- Level 2 开始前创建或更新项目级 `AGENTS.md`，记录产品边界、所有权、禁止项、闸门、验证和最终 Acceptance。
- 不覆盖用户已有规则；只增加当前项目需要的最小合同。
- 需要模板时读取 [templates.md](references/templates.md)。

### 4. 派发 Level 1 subagent

- `spawn_agent` 适用于符合全部 Level 1 条件的内部临时任务；不得用它冒充已判定为 Level 2 的用户可见任务。
- 每个 `spawn_agent` 调用前，路由表中必须有对应行，并明确写出 `Level 1`、`侧边栏可见：否`、`执行载体：spawn_agent`。
- 只派发具体、独立、边界清楚的侦察、验证或短期实施。默认只读；用户和适用规则允许时可做边界明确的短期修改，但主任务必须保持最终所有权、整合修改并复核结果。
- 任务书必须自包含，写明搜索范围、精确问题、允许修改范围和输出格式；要求 `file:line`、符号名、关键原文、补丁或来源链接。
- 独立问题在当前规则允许时并行派发；禁止并行修改重叠文件。遵循工具要求等待结果后再据此行动。
- 把 subagent 结果视为有损压缩后的交付。按引用点做小范围核验，不重复通读已委派的大范围材料。
- 主任务最终回复前必须等待 Level 1 完成并验收，不能让一次性 subagent 留下后续职责。
- Level 1 一旦发现需要跨轮次状态、用户直接介入、独立所有权、正式交接或长期恢复，必须停止继续实施并返回当前发现、已生成产物、升级原因和下一步；由主任务按授权创建 Level 2，不得让 subagent 静默演变成长任务。
- Level 2 可见任务内部仍可使用符合这些条件的 Level 1 subagent。

### 5. 派发可见交付任务

- 使用自包含任务书，不假设新任务自动继承主任务全部历史。
- 在任务书中给出项目路径、上游状态、所有权、禁止范围、Acceptance、验证命令和完成报告格式。
- 创建前只解析实际需要的真实项目、主机、环境、分支和模型参数；使用项目时查询真实项目及其 Git 属性，禁止编造 project ID、thread ID、host ID、模型、分支或 worktree 状态。projectless 或 fork 场景不做无关查询。
- 使用可创建或 fork 用户可见任务的工具。创建失败或能力不可用时立即停止并说明；未获用户同意不得降级为 `spawn_agent`。
- 首个 Level 2 编排检查点必须通过任务列表确认每个目标任务真实存在，并核对 thread ID、标题、项目、环境和状态。只有 client ID 或仍在排队时明确报告 `pending`，不得声称任务已就绪；可读取时再抽查任务内容。
- 完整总管模式下，主任务只管理、决策和验收，不在已派发的业务所有权范围内并行写代码。
- 每个实现任务完成后，由主任务核对范围、接口、检查结果和下游可用性，再启动依赖它的任务。

### 6. 监听与闸门

- 优先使用 wait/snapshot 能力跟踪可见任务；不要用高频重复读取制造噪声。
- 等待采用自适应节奏：任务刚派发后的首次等待为 2 分钟，用于尽早发现路径、权限、编译或启动阻塞；确认进入稳定实现后，默认一次 `wait_threads` 等待 10 分钟。任务完成、需要输入或状态变化应提前唤醒，不必等满 10 分钟。
- 10 分钟无变化时才读取压缩快照并干预：检查是否卡在工具调用、等待输入、错误循环或未满足的交接门。收到明确进度且无阻塞后，再等待 10 分钟；不要恢复固定 5 分钟轮询。
- 短命令、首次启动、刚修复后等待测试结果可继续使用 1–2 分钟等待；这是例外，不是长实现任务的默认值。
- 只向用户报告关键里程碑、决策、阻塞、闸门结果和返工闭环。
- “任务自报完成”不是通过。核对实际修改、命令输出、产物和未验证项。
- 保留原始环境错误；禁止用 shim、`0 tests`、权限绕过或文字推断制造假绿。
- 需要完整闸门时读取 [gates-and-evidence.md](references/gates-and-evidence.md)。

### 7. 独立 QA 与 Repair

- 让 QA 保持只读。QA 报告必须包含文件/行号、复现场景、期望行为、影响和未验证原因。
- 缺陷成立后，为每个独立根因创建最小 Repair 任务；不要让 QA 顺手修复。
- Repair 只改获准范围，留下最小回归检查，完成后交回原 QA 复验。
- 将工具链或权限阻塞记录为环境边界，不把它误写成产品通过或产品缺陷。

### 8. 最终交付

分别报告：

- 用户可见产物及入口；
- 实际修改范围；
- 自检、测试、Debug、Release、打包结果；
- 真实数据或外部事实交叉核对；
- 可见 UI 与运行状态；
- 安全、隐私、联网、权限和发布边界；
- 未验证项、原因及影响。

不要用“构建成功”代替“用户看得到”，不要用“进程存在”代替“交互已验证”。

## 停止条件

完成所有已授权范围且证据闭环后停止。若完成需要新的业务选择、外部协调、破坏性动作或范围扩展，报告已完成部分和唯一阻塞，等待用户决定。
